Caso aplicativo: InkaShop

Cadena retail peruana con 45 tiendas, más de 2 millones de clientes, 120,000 transacciones diarias y un presupuesto aprobado de S/. 2,000,000. Usa Excel y SQL Server, y sus reportes tardan de 3 a 5 días.

Por qué es un problema de Big Data

  • Volumen: la escala supera a las hojas de cálculo y a las bases relacionales.
  • Velocidad: Falabella y Ripley analizan en tiempo real; InkaShop no.
  • Variedad: redes sociales, logs de la app, correos y sensores IoT quedan sin explotar.
  • Falla entre las etapas de Almacenamiento y Tratamiento, lo que anula la Representación.

Ciclo de gestión propuesto

  • Captura: Apache Flume, Kafka, APIs REST, conectores JDBC y web scraping.
  • Almacenamiento: Data Lake en Hadoop (HDFS), NoSQL (MongoDB) y Data Warehouse con Data Marts.
  • Tratamiento: Apache Spark, Python o R y Machine Learning. Batch para históricos y streaming para alertas.
  • Representación: dashboards en tiempo real y mapas de calor.

Caso de uso: demanda navideña

Se combinan 5 años de POS, stock logístico, wishlist de la app y tendencias en redes. Spark y Python calculan la velocidad de venta por ciudad y emiten alertas de reabastecimiento. Beneficios: menos quiebres de stock, menor costo de inventario y despachos proactivos.

Modelado, gobernanza y ética

  • Niveles de modelado: conceptual (directivo), lógico (analítico) y físico (técnico).
  • Tipo de modelo: NoSQL documental para el catálogo, relacional (ACID) para pagos y dimensional (estrella) para análisis de ventas.
  • Gobernanza: Comité de Datos, Data Stewards, diccionario único y linaje con Apache Atlas.
  • Ética y privacidad: anonimización, cifrado, cumplimiento de la Ley N° 29733 y centro de preferencias de privacidad.

Sesión 3: Ecosistema Big Data y Docker

Pilares tecnológicos

  • Almacenamiento distribuido: HDFS.
  • Procesamiento: Spark (en memoria) y Flink (streaming).
  • Orquestación de flujos: Apache Airflow para pipelines ETL.
  • Contenedores: Docker y Kubernetes.

Máquinas virtuales vs. contenedores

Máquina virtualContenedor Docker
Sistema operativoUno completo por VMComparte el kernel del host
RecursosAlto consumo de CPU, RAM y discoLigero y rápido

Conceptos

  • Imagen: plantilla de solo lectura, como una "clase".
  • Contenedor: instancia en ejecución, como un "objeto".
  • Docker Hub: registro público de imágenes.
  • VS Code: editor recomendado, con extensión de Docker.

Comandos básicos

docker pull <imagen>
docker images
docker run -it -d <imagen>
docker ps
docker stop <ID>   /   docker rm <ID>
docker exec -it <ID> <comando>

Dockerfile

Receta para construir una imagen. Directivas: FROM, WORKDIR, COPY, RUN, EXPOSE.

docker build -t mi-web-app:v1 .
docker run -p 8081:80 mi-web-app:v1

Luego se accede desde localhost:8081.

Sesión 4: Orquestación con Docker Compose

Ejecutar docker run a mano para cada contenedor es propenso a errores. Docker Compose define y ejecuta aplicaciones multi-contenedor desde un solo archivo YAML.

Propósito

  • Automatizar el inicio y el ciclo de vida de los servicios.
  • Simplificar la comunicación mediante redes virtuales.
  • Reproducir el mismo entorno en desarrollo, pruebas y producción.

Directivas de docker-compose.yml

DirectivaFunción
versionSintaxis (las diapositivas usan 3.8)
servicesDefine cada contenedor
build / imageConstruir desde Dockerfile o usar imagen existente
portsMapea puerto del host al del contenedor
environmentVariables de entorno
depends_onOrden de inicio
networks / volumesRedes y persistencia (opcionales)

YAML exige indentación correcta: un espacio mal puesto genera error.

Comandos

docker compose up        # añade --build para reconstruir
docker compose down
docker compose ps
docker compose logs

Práctica: Flask + Redis

  • El servicio web se construye con un Dockerfile y requirements.txt.
  • El servicio db usa la imagen redis:alpine.
  • app.py incrementa un contador con redis.incr('hits').
  • Se accede por el puerto 5000 y muestra "¡Hola Mundo! Visto X veces".
